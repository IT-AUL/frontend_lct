# Архитектура DeckDNA Web

Фронтенд — статический SPA. Бэкенд FastAPI в
[отдельном репозитории](https://github.com/Ranel435/LCT-prezi-2026) выполняет разбор документов,
планирование, вёрстку, аудит и экспорт. Браузер управляет решениями пользователя и показывает
полученные данные. Контракт типизирован в `src/shared/api/schema.d.ts`; транспорт — openapi-fetch,
серверное состояние — TanStack Query, навигация — React Router 7.

## 1. Поток данных и семь шагов

Серверный конвейер: **парсинг шаблона и материалов → смысловые блоки и выводы → план →
вёрстка по правилам шаблона → аудит → экспорт**. Пользователь подтверждает содержание до полной
сборки; аудит и экспорт доступны вместе с доводкой выбранного варианта.

Маршруты объявлены в `src/app/router`, шаблоны и функции URL — в `src/shared/config/routes.ts`.
`/` — список проектов (`pages/projects`), создание — `features/create-project`.
Далее все пути относятся к `/projects/:projectId`. В таблице API опущен префикс `/api/v1`.

| Шаг и маршрут | Страница и основные блоки | API и действия |
|---|---|---|
| 1. Материалы, `/start` | `pages/intake`, `widgets/intake-board`, `widgets/design-dna`: идея, файлы и их типы, паспорт шаблона, палитра и шрифты, правила и JSON ДНК, брендбук и приоритет | `POST /projects/{id}/intake`; `PATCH /projects/{id}/intake/files/{name}`; `GET /templates/{id}/summary`, `/templates/{id}`, `/templates/{id}/design-dna`; `GET /brandbooks/{id}/summary`, `PATCH /brandbooks/{id}` |
| 2. Что понял, `/understanding` | `pages/understanding`, `widgets/draft-deck`: смысловые блоки, источники, таблицы, графики, выводы и подтверждение; правки блоков, исключение и новые тезисы | `GET /content-packs/{id}/understanding?use_llm=…`; `PATCH /content-packs/{id}/blocks`, `/content-packs/{id}/insights/{insight_id}`; `POST /content-packs/{id}/notes`; `GET /projects/{id}/questions` для выбора следующего шага |
| 3. Вопросы, `/questions` | `pages/questions`: вопросы с причиной, варианты и свой ответ, пропуск необязательных уточнений, решение при нехватке материала и сводка колоды; пустой список ведёт сразу к плану | `GET /projects/{id}/questions`; `POST /projects/{id}/answers`; при добавлении тезисов — `POST /content-packs/{id}/notes`; затем запрос плана |
| 4. План, `/plan` | `pages/plan`, `widgets/deck-plan`, `features/edit-deck-plan`: главная мысль, сторилайн, редактирование слайдов, пунктов и визуала, объяснение графиков и источники | `POST /projects/{id}/plans` с `respond_async: true`; `GET /projects/{id}/plans/{plan_id}` (при восстановлении также `GET /plans/{plan_id}`); `PATCH /plans/{id}/slides/{slide_id}`; `POST /plans/{id}/slides/{slide_id}/actions`, `/plans/{id}/slides/{slide_id}/research` |
| 5. Стиль, `/style` | `pages/style`: три колонки с пробными слайдами, рекомендация, сравнение одного слайда, выбор одного стиля или всех трёх, режим сборки | `POST /plans/{id}/style-previews` с `respond_async: true`; `GET /style-previews/{id}`; события `preview.ready`; изображения через `/artifacts/{id}/download`; запуск `POST /projects/{id}/generations` с выбранными `variants`, правленым `deck_plan` и при наличии `preview_id` |
| 6. Сборка, `/runs/:runId` | `pages/generation`, `widgets/generation-tracker`: этапы, варианты, лента черновиков и готовых слайдов, инспектор, отмена, повтор и переход к доводке | `GET /generations/{id}`, `/jobs/{id}`, `/generations/{id}/variants`, `/variants/{id}/slide-drafts`; SSE `/jobs/{id}/events`; `POST /generations/{id}/cancel`, `/generations/{id}/retry` |
| 7. Доводка, `/runs/:runId/polish/:variantId?` | `pages/audit`, `widgets/audit-workspace`, `widgets/slide-inspector`: лента, превью и рамки, вкладки слайда, проблем и журнала; переделка слайда, объяснение, заметки и источники; скачивание и паспорт | `GET /variants/{id}`, `/variants/{id}/slides`; `POST /variants/{id}/audits`; `GET /audits/{id}`, `/audits/{id}/issues`; `POST /audits/{id}/repairs` (также `?dry_run=true`), `/issues/{id}/dismiss`; `GET /slides/{id}/explain`; `POST /variants/{id}/slides/{slide_id}/regenerate`; `POST /variants/{id}/exports`; `GET /exports/{id}`, `/artifacts/{id}/download` |

Сессия `GET /projects/{id}/session` связывает шаги с актуальными идентификаторами материалов,
плана, превью и сборки. «Сделай сам» вызывает `POST /projects/{id}/session/autopilot` с
`from_step`; UI наблюдает job и открывает сборку. Навигация и общий каркас находятся в
`widgets/assistant-bar` и `widgets/step-shell`.

Самостоятельных страниц старого сценария больше нет. Старые URL сохранены только как
перенаправления в `ProjectRedirect`: загрузка и бриф ведут в материалы, старый план — в текущий
план, адреса вариантов, аудита и экспорта — в доводку. Модуль `pages/audit` реализует седьмой шаг;
отдельного слайса страницы доводки нет. Без `variantId` открывается доступный вариант, в первую
очередь сбалансированный.

Системные данные: `GET /capabilities`, `/version`, `/skill/manifest`, при поддержке — `/audit/rules`.
Подключение провайдера использует `/provider-sessions`, `/provider-sessions/{id}`,
`/provider-sessions/{id}/test`; вызовы внешнего сервиса выполняет бэкенд.

## 2. Слои Feature-Sliced Design

| Слой | Ответственность и расположение |
|---|---|
| `app` | Инициализация, QueryClient, тема, роутер, корневой и проектный layouts, глобальные стили |
| `pages` | Композиция маршрутов: `projects`, `intake`, `understanding`, `questions`, `plan`, `style`, `generation`, `audit`, `not-found` |
| `widgets` | Крупные блоки: загрузка и паспорт, колода смысловых блоков, план, трекер сборки, рабочая область аудита, инспектор, паспорт качества, навигация и настройки |
| `features` | Действия: создание проекта, правка плана, отмена и повтор сборки, выбор проблем, repair и dismiss, получение файлов, экспорт и команда воспроизведения |
| `entities` | Проекты, шаблоны, контент-паки, планы и сборки, варианты, аудит, паспорт, сессия провайдера, возможности системы; `assistant` содержит контракт семи шагов, нормализацию, хуки и SSE |
| `shared` | Типизированный API, обработка ошибок и загрузка с прогрессом, MSW, конфигурация, библиотечные функции, PDF, дизайн-токены и UI-примитивы |

Импорты идут вниз по слоям через публичный `index.ts` с алиасом `@/`. Разрешённые связи сущностей
объявлены через `@x`. Сегменты `api`, `model`, `lib`, `ui` отделяют транспорт, состояние, вычисления
и представление. Границы проверяет `npm run lint:fsd` (Steiger).

## 3. Состояние и обновления

TanStack Query кэширует серверные данные по идентификаторам. После правок инвалидируются связанные
материалы, сессия, план, превью, варианты и аудит. Нормализация в `entities/assistant/model/normalize.ts`
поддерживает неполные ответы; на новых необязательных ручках 404/405/501 превращаются в `null`.
Ошибки остальных запросов сохраняют сообщение, код и сведения сервиса.

Состояние страницы (выбранная карточка, раскрытая панель, флажки) хранится в React; номер слайда
доводки — в query-параметре `slide`. В браузере сохраняются черновики и запросы плана, исключённые
источники, история прогонов, журнал и отметки этапов проекта. Это локальные данные данного браузера,
а не общий серверный журнал. Метаданные сессии провайдера хранятся в `sessionStorage`, токен после
отправки серверу не сохраняется.

Если общая загрузка недоступна, шаг материалов использует прежние `POST /projects/{id}/templates`
и `POST /projects/{id}/content-packs`. Если нет ручки понимания, используются доступные секции
контент-пака. Пробные изображения, дополнительные метрики и объяснения появляются по данным API;
отсутствие новой ручки не означает поддержку её результата.

## 4. План и живая сборка

Запрос плана поддерживает готовый ответ и `202` с job. В асинхронном случае UI читает события
исследования и `plan.slide`, опрашивает job и получает готовый план. Отмена построения вызывает
`POST /projects/{id}/plans/{plan_id}/cancel`. Отредактированный план передаётся в сборку целиком
в `deck_plan`, чтобы вёрстка использовала решения пользователя.

Трекер сборки (`entities/generation`) сразу выдаёт локальный `local-…` и открывает экран прогресса,
не дожидаясь ответа POST. После получения `generation_id` и `job_id` адрес заменяется настоящим.
Так поддерживаются и синхронная обработка, и асинхронный job. Пока сервер не сообщил этап,
UI не вычисляет процент готовности. После перезагрузки незавершённого POST результат ищется через
последний прогон проекта; если восстановить его нельзя, показывается потеря связи с запуском.

SSE-клиент (`entities/assistant/api/events.ts`, `lib/sse.ts`) получает `/jobs/{id}/events`,
восстанавливает соединение с `after` и `Last-Event-ID`, отбрасывает повторные sequence и завершает
чтение по терминальному событию. События `preview.ready`, `stage.started`, `slide.ready`,
`variant.completed` и `job.completed` обновляют показ. Параллельно опрашиваются сборка и job,
а `/variants/{id}/slide-drafts` предоставляет реальные черновики. Запуск передаёт
`progressive_previews: true`. При отсутствии потока остаются серверные статусы и готовые файлы;
появление слайдов по одному зависит от реализации сервера.

Пользователь может осмотреть готовый слайд прямо во время сборки. При завершении предусмотрен
автопереход к доводке; открытие инспектора или явная отмена перехода оставляют на экране сборки.

## 5. Превью, аудит и экспорт

Если `/capabilities` заявляет PNG-превью и слайд содержит нужные ссылки, инспектор использует
картинку. Резервный путь — страница PDF, которую рисует лениво загружаемый pdf.js в legacy-сборке.
Если доступного изображения нет, рамки могут отображаться на листе с пропорциями слайда.
Координаты `bbox` нормированы к размеру слайда; выход за границу обрезается.

Седьмой шаг объединяет аудит, выбор варианта, правки одного слайда, скачивание и паспорт.
D и N определяются полем `deterministic`, статусы частей берутся из `AuditRun`. Предпросмотр repair
включается флагом `repair_dry_run`. Журнал учитывает результаты отдельных исправлений и сверяет
их с повторным аудитом; идентичность проблемы задаётся `fingerprint`, резервно — правилом,
номером слайда и фигурами. Подробности — в [docs/AUDIT_UI.md](docs/AUDIT_UI.md).

Экспорт: UI читает записи `/exports/{id}` и артефакты выбранного варианта; при необходимости
заказывает формат через `/variants/{id}/exports`. HTML доступен, если заявлен в capabilities;
ответ 501 переводит действие в недоступное состояние. Проверяется ревизия файла относительно
аудита: устаревший PDF или паспорт не выдаётся за результат новой правки. Паспорт открывается
в панели на том же экране. Состав и нативность файлов проверяет сервер.

Переключатель режима сборки на шаге стиля пока меняет локальное состояние и подпись, но
не добавляет режим в запрос сборки. Выбор одной или трёх стратегий передаётся в API.

## 6. Mock-режим

`VITE_API_MODE=mock` подключает MSW из `src/shared/api/mocks` до старта интерфейса.
Service Worker перехватывает запросы того же API в браузере. Обработчики используют записанные
ответы, фикстуры семи шагов, PDF из `public/mocks` и состояние в памяти. Они эмулируют создание
проекта, загрузку, вопросы, план, пробные стили, события, сборку, аудит, repair и экспорт.

Загруженный файл не проходит настоящий разбор; варианты и превью основаны на фикстурах,
скачиваемый mock PPTX — упрощённый тестовый файл. Контекстные проверки и прогресс имитируются.
В базовом mock-каталоге HTML отключён и возвращает 501. Режим пригоден для разработки и проверки
сценариев без API, но не подтверждает качество презентации или выполнение серверных требований.
В обычном режиме `live` MSW не запускается.

## 7. Запуск и поставка

Полные команды и переменные перечислены в [README.md](README.md). `npm run dev` и `dev:mock`
запускают Vite; `build` создаёт `dist`, `preview` раздаёт сборку. Vite проксирует `/api` на
`BACKEND_URL` без переписывания пути.

Docker собирает статику в `node:22-alpine` и раздаёт через `nginx:1.28-alpine`. API-режим —
build argument, адрес API — переменная запуска. `docker/nginx.conf.template` обеспечивает
SPA fallback, прокси, длительные запросы, SSE без буферизации и кэш хэшированных ресурсов.
`/healthz` проверяет web. Compose запускает web, а профиль `backend` — ещё и API из соседнего клона.

## 8. Проверки и границы гарантий

Vitest и Testing Library проверяют нормализацию, клиентское состояние, обработку событий,
план, превью, аудит, исправления, экспорт и компоненты; контрактные тесты проверяют MSW.
`npm run e2e` проходит mock-сценарии в Chromium, Firefox и WebKit.
`npm run e2e:live` проходит семь шагов с настоящим PPTX на заданном API и создаёт тестовые данные.
Статические проверки — `lint`, `lint:fsd`, `typecheck`; сборка — `build`.

Целевая ширина — от 1280 px, браузеры — актуальная и предыдущая версии Chrome, Firefox,
Safari и Яндекс Браузера. Сборка использует `es2022`, шрифты поставляются локально.
Тестирование WebKit/Chromium не заменяет отдельную проверку Safari/Яндекс Браузера.

Извлечение правил произвольного шаблона, точность выводов, различия вариантов, нативные объекты,
полнота D/N, время сборки и формат HTML зависят от бэкенда. Трассировка требований и ограничения
приведены в [docs/REQUIREMENTS.md](docs/REQUIREMENTS.md), обоснование вариантов — в
[docs/VARIANTS.md](docs/VARIANTS.md).
