# Выкатка и эксплуатация DeckDNA

Фронт (`IT-AUL/frontend_lct`) и бэк (`Ranel435/LCT-prezi-2026`) собираются в GitHub Actions, публикуются в GHCR и выкатываются
на сервер по SSH с автоматической проверкой и откатом. На сервере же работает панель наблюдаемости для DevOps и SRE.

## Архитектура

```
Интернет ── 80/443 ──► Caddy (уже стоит на сервере, Let's Encrypt, /etc/caddy/apps.d)
                         ├─ https://<APP_DOMAIN> ──► 127.0.0.1:18100 ─► web (nginx) ── /api ──► api (uvicorn + LibreOffice)
                         └─ https://<OPS_DOMAIN> ──► /      ─► 127.0.0.1:18101 ─► Grafana (логин)
                                                    /logs ─► 127.0.0.1:18102 ─► Dozzle (basic auth)

сеть docker "deckdna" (без публикации портов наружу)
  наблюдаемость:  VictoriaMetrics (метрики, 30 дней) · VictoriaLogs (логи, 14 дней) · Vector (сбор логов)
                  node-exporter (хост) · cAdvisor (контейнеры) · Blackbox (пробы и сертификат) · docker-socket-proxy (только чтение)
```

Порты `18100–18102` слушают только `127.0.0.1`. Наружу торчит лишь Caddy. Бэк напрямую из сети недоступен: запросы идут через nginx фронта (`/api/`).

## Что где лежит на сервере

| Путь | Назначение |
|---|---|
| `/srv/deckdna/shared/.env` | секреты и настройки (пароли, домены, провайдер моделей), права `600` |
| `/srv/deckdna/releases/` | распакованные релизы (хранятся 6 последних) |
| `/srv/deckdna/current` | ссылка на активный релиз |
| `/srv/deckdna/state/` | `current.env`, `previous.env`, `history.jsonl` (журнал выкаток), `deploy.log` |
| `/srv/deckdna/config`, `/srv/deckdna/rendered` | конфигурация наблюдаемости и отрендеренные шаблоны |
| `/etc/caddy/apps.d/deckdna-{app,ops}.caddy` | виртуальные хосты, обновляются скриптом `caddy-apply` |
| `/opt/deckdna/bin/` | два файла, принадлежащие root: точка входа SSH и `caddy-apply` |
| `/srv/backups/deckdna/` | ежедневные архивы (03:17), хранятся 7 дней |

## Панель для DevOps и SRE

| Что | Где | Доступ |
|---|---|---|
| Дашборды, алерты, поиск по логам | `https://<OPS_DOMAIN>/` (Grafana) | пользователь `admin`, пароль в `.env` |
| Живые логи контейнеров и их состояние | `https://<OPS_DOMAIN>/logs` (Dozzle) | basic auth: `ops` и пароль в `.env` |

Пароли: `ssh ubuntu@<host> 'sudo grep -E "^(GRAFANA_ADMIN_PASSWORD|OPS_BASIC_AUTH_PASSWORD)=" /srv/deckdna/shared/.env'`.

Дашборды (папка `DeckDNA`):

- **Обзор** — доступность сайта и API, срок сертификата, время ответа, число контейнеров, трафик, статусы, задержки, нагрузка хоста.
- **Контейнеры** — состояние каждого контейнера (работает или остановлен), аптайм, перезапуски и OOM за сутки, CPU, память от лимита, сеть.
- **Трафик и заходы** — запросы, уникальные IP, ошибки 4xx и 5xx, p50/p95/p99, топ путей, IP и клиентов, последние ошибочные запросы (по access-логам Caddy).
- **Логи** — все сервисы стека с фильтром по сервису и полнотекстовым поиском.

Дашборды генерируются из кода: `python3 deploy/tools/generate_observability.py`, затем коммит. Правки в интерфейсе Grafana не попадают в репозиторий.

### Алерты

12 правил Grafana в папке `DeckDNA`: сайт и API недоступны, панель ops недоступна, медленный ответ, срок сертификата меньше 14 дней, остановленный контейнер, цикл перезапусков, OOM, память API у лимита, диск больше 85%, память хоста и swap.
Каналы уведомлений не настроены: без токена бота это невозможно. Чтобы получать сообщения, добавьте contact point (Telegram, Slack, e-mail) в Grafana: *Alerting → Contact points*, затем назначьте его в *Notification policies*.

## Как устроены релизы

Workflow `.github/workflows/deploy.yml`:

| Событие | Что происходит |
|---|---|
| Успешный CI на `main` | собирается образ фронта, выкатывается с текущим бэком |
| Тег `vX.Y.Z` | то же для помеченного коммита |
| Каждые 20 минут | проверяется `main` бэка; если появился новый коммит, собирается его образ и выкатывается с текущим фронтом |
| Ручной запуск (*Run workflow*) | выкатка любых ссылок фронта и бэка или откат |

Порядок выкатки: план (что запущено, что нужно) → сборка отсутствующих образов → распаковка релиза на сервере → обновление ops-стека → `docker compose up --wait` приложения → перезагрузка Caddy (с валидацией) → **сквозной дымовой тест** (создание проекта, загрузка шаблона, генерация, скачивание PPTX) → запись в журнал.
Если проверка не прошла, предыдущая версия возвращается автоматически. Образы фронта и бэка не удаляются, пока на них ссылается текущий или предыдущий релиз.

Чтобы зафиксировать версию бэка, запустите workflow вручную с `backend_ref` (коммит или тег): плановая проверка возьмёт новый коммит только при следующем запуске, если ссылка снова не задана.

### Откат

- GitHub: *Actions → Deploy → Run workflow → action = rollback*.
- С машины с ключом: `ssh -i ~/.ssh/deckdna-ci-deploy deckdna@<host> rollback`.

### Секреты GitHub

| Тип | Имя | Значение |
|---|---|---|
| secret | `DEPLOY_SSH_KEY` | приватный ключ пользователя `deckdna` |
| variable | `DEPLOY_HOST` | адрес сервера |
| variable | `DEPLOY_KNOWN_HOSTS` | отпечаток хоста (`ssh-keyscan -t ed25519 <host>`) |
| variable | `APP_URL` | публичный адрес приложения |

## Модель безопасности

- Ключ CI открывает **только** три команды (`deploy`, `rollback`, `status`) через принудительную команду `/opt/deckdna/bin/entrypoint`; интерактивный вход, проброс портов и любые другие команды запрещены, аргументы проверяются по белому списку.
- Домашний каталог пользователя `deckdna` принадлежит root, `authorized_keys` тоже: ключ нельзя использовать, чтобы обойти ограничения.
- Единственное право root у `deckdna` — запуск `caddy-apply` для двух своих виртуальных хостов. Скрипт проверяет конфигурацию Caddy и при ошибке возвращает старые файлы.
- Токен реестра передаётся в SSH-потоке на время выкатки и удаляется после `docker logout`; долгоживущих токенов на сервере нет.
- Контейнеры работают с `no-new-privileges`, лимитами памяти и процессов, ротацией логов; у API сброшены все capabilities, у nginx корневая файловая система только для чтения.
- Доступ к Docker для панели идёт через `docker-socket-proxy` (только чтение), Dozzle видит лишь контейнеры этого стека.

## Ресурсы

Сервер общий (GitLab, Ollama и другие сервисы), поэтому у каждого контейнера жёсткий лимит: API 1,5 ГБ, стек наблюдаемости около 1,3 ГБ вместе. Значения задаются в `.env` (`API_MEM_LIMIT`, `API_CPUS`).

## Частые операции

| Задача | Как |
|---|---|
| Сменить домен | поправить `APP_DOMAIN` и `OPS_DOMAIN` в `.env`, создать A-записи на IP сервера, запустить workflow |
| Включить языковую модель | в `.env`: `DECKDNA_MOCK_PROVIDER=false`, `DECKDNA_PROVIDER_BASE_URL`, `DECKDNA_PROVIDER_API_KEY`, `DECKDNA_MODEL_TEXT`, `DECKDNA_MODEL_VISION`, затем запустить workflow (только открытые модели до 35B по ТЗ) |
| Посмотреть состояние | `ssh -i ~/.ssh/deckdna-ci-deploy deckdna@<host> status` |
| Журнал выкаток | `/srv/deckdna/state/history.jsonl` |
| Перевыпустить ключ CI | `ssh-keygen -t ed25519 -f key`, затем `sudo bash scripts/bootstrap.sh key.pub <app> <ops>` и обновить секрет |

## Ограничения

- Хранилище бэка находится в памяти процесса: **проекты, прогоны и загруженные файлы пропадают при каждой перезагрузке или выкатке API**. Это свойство бэка, а не выкатки.
- API работает в одном процессе (`--workers=1`): иначе состояние разъехалось бы между процессами.
- Плановая проверка бэка не запускается в неактивных репозиториях дольше 60 дней (ограничение GitHub).
- До появления настоящего домена сертификаты выпускаются для имён на `sslip.io`; общий лимит Let's Encrypt для этого домена может задержать выпуск.
