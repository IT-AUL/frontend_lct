# 11 · План разработки фронта (черновик брейншторма, 25.09.2026)

Цель: отдельный фронт (`frontend_lct`), который раскрывает сильные стороны DeckDNA и прячет
слабые. Разрабатываем параллельно бэку; когда на бэке появятся нужные эндпоинты, подключаемся к ним.
Поставка: Docker-образ; CI выкладывает два образа (front + back) на VPS.
Их `frontend/` игнорируем.

## Позиционирование и ориентиры рынка

Мы «компилятор корпоративных презентаций», а не генератор по промпту. Ориентиры по экранам
(подробно — `docs/14-competitive-landscape.md`): ДНК шаблона — Copilot, но без подготовки
шаблона; план до вёрстки — Gemini и SlidePoint; панель аудита — empower Design Check;
очередь исправлений, до/после и оценка соответствия — Prezent; привязка фикса к правилу —
Templafy; нативный PPTX как главное обещание — Plus AI. Сквозной принцип: **доказательства,
а не обещания**.

## Принципы

1. **Работа на двух источниках.** Везде, где можно, берём данные из живого бэка: он поднимается локально
   через `docker compose` и работает без LLM за секунды. Чего на бэке ещё нет, берём из **MSW-моков**
   с данными, записанными с реального бэка. Переключение — флагом `VITE_API_MODE=live|mock|hybrid`.
2. **Слой адаптеров.** Экраны не знают, как бэк реализует функцию.
   `useSlidePreviews(variant)` сначала берёт PNG с бэка, а если его нет — рендерит страницы из PDF через pdf.js.
   `useGenerationTracker(run)` одинаково работает и с синхронным, и с асинхронным POST.
3. **Возможности из `/capabilities` и `/version`.** Если функция на бэке ещё не готова (HTML-экспорт),
   показываем это честно (бейдж «скоро» или тултип), а не выводим битую кнопку.
4. **Никакой доменной логики во фронте**, только отображение и оркестрация.
5. Типы берём из `/openapi.json` через openapi-typescript. `npm run gen:api` запускается на живом бэке,
   для офлайна копия лежит в репо.

## Как закрываем слабые места бэка на фронте

| Разрыв бэка | Что делаем на фронте |
|---|---|
| Нет PNG-превью слайдов | **pdf.js**: рендерим страницы PDF варианта в canvas. Это даёт превью, миниатюры, montage и подложку для bbox-оверлея: координаты [0,1] ложатся на страницу |
| Нет превью шаблона | Design DNA рисуем сами: палитра, образцы шрифтов, шкала кеглей, **схемы макетов по bbox плейсхолдеров**, якоря (лого/футер) на пустом «листе» с правильным aspect ratio |
| Генерация синхронная, ответ идёт минуты | Сразу после клика переходим на экран прогона: таймер против бюджета 5 минут и честные стадии пайплайна (без поддельного прогресса). Когда вольют async-ветку, адаптер переключится на реальные статусы |
| SSE — заглушка | Опрашиваем `GET /generations/{id}` и `/jobs/{id}` каждые 1.5–2.5 с |
| После repair у варианта остаётся только pptx, PDF пропадает | «До» показываем по старому PDF, «после» — списком применённых действий и статусами issues. Просим бэк перерендерить PDF |
| HTML-экспорт → 501 | Кнопка управляется через capabilities; просим бэк подключить `render_html` |
| Контент-пак парсит только первый файл | Даём вставить бриф текстом: textarea → `brief.md` (File) на клиенте. Предупреждаем, что учитывается один файл |
| Нет GET-списка provider-сессий | id сессии храним в памяти/sessionStorage, токен — никогда |

## Экраны (по пути демо)

0. **Оболочка**: верхняя панель (проект, статус бэка/провайдера, версия скилла), боковой степпер
   сценария «Шаблон → Бриф → Генерация → Варианты → Аудит → Экспорт», тосты, обработка ошибок
   из error envelope.
1. **Старт / проекты**: список проектов (статус, шаблон, последний прогон). Кнопка «Демо» создаёт
   проект по готовому сценарию, это страховка на защите.
2. **Шаблон → Design DNA** (главный wow-экран): drag&drop PPTX/POTX с прогрессом загрузки
   (файлы до 25 МБ), затем анимированное «вскрытие» шаблона. Показываем палитру (theme + observed
   с частотами), шрифты **заявлено / фактически** (подсвечиваем расхождения), шкалу кеглей,
   поля и сетку, фоны, якоря, роли слайдов с confidence, схемы макетов и неподдерживаемые фичи.
   Этим показываем жюри, что шаблон читается как набор правил.
3. **Бриф и контент**: назначение фича/продукт/проект/инициатива (по ТЗ), аудитория, число
   слайдов (по умолчанию 10–15 или своё), язык, тон, обязательные разделы. Файлы или вставка текста.
   Есть превью распарсенного ContentPack (секции, таблицы, числа, будущие графики) и граф evidence.
   Переключатель LLM и выбор провайдера.
4. **Генерация**: таймер против бюджета 5 минут (NFR виден жюри), стадии, три карточки вариантов,
   которые заполняются по мере готовности. Отмена и повтор.
5. **План колоды (FR-07), «сначала план, потом вёрстка»**: purpose, заголовок-вывод, источник
   у каждого слайда. Целевой UX — подтверждение и правка плана до вёрстки. В v1 (без ручки)
   план показываем после генерации с действием «изменить и пересобрать».
6. **Сравнение трёх вариантов**: три колонки с миниатюрами (pdf.js), синхронная прокрутка,
   **ось различий с описанием стратегий** (обоснование по ТЗ), метрики (validity, PEI
   редактируемости, issues по severity), кнопки «Открыть», «Аудит», «Скачать».
7. **Просмотр и аудит** (ориентир: empower + Prezent): сводка соответствия шаблону сверху,
   категории-«пакеты политик», фикс в один клик у каждой проблемы, журнал изменений,
   финальное состояние «повторный аудит — 0 критических».
   Дальше детали: лента миниатюр с бейджами issues, большой слайд с **bbox-оверлеем**
   (цвет по severity, hover и клик), список issues с группировкой и фильтрами. Каждая проверка
   помечена **D (правило) или N (модель)**, это спросят на защите. Карточка: измерено против
   порога, evidence, предложенный фикс. Выбрать issues → «Исправить» → repair job → новая ревизия.
   Статусы fixed/unresolved, dismiss с причиной, повторный аудит (VLM по сессии).
8. **Экспорт и Quality Passport** (редактируемость — главное обещание, показываем доказательство round-trip): PPTX (бейдж editable), PDF, HTML, JSON паспорта; паспорт
   в визуальном виде (метрики, fallbacks, provenance: версии скиллов, промптов и моделей — FR-24).
   Кнопка «скопировать команду воспроизведения».
9. **Настройки провайдера**: drawer, тест возможностей (ok/fail/skip), предупреждение про токен.
10. **О системе**: `/version`, `/capabilities`, `/skill/manifest`, 24 правила аудита.

## Стек (предложение)

React 18 + TypeScript strict + Vite, React Router, TanStack Query, zustand (UI-состояние),
**Tailwind + Radix/shadcn-примитивы**, чтобы быстро получить хороший вид, framer-motion,
pdfjs-dist, MSW, Vitest + Testing Library, Playwright (Chromium/Firefox/WebKit ≈ Safari).
Только десктоп, min-width 1280.

## Docker и деплой

- Многостадийный `Dockerfile`: node:20 build → nginx:alpine со статикой.
- `nginx.conf.template` + envsubst: `BACKEND_URL` задаётся **в рантайме** (один образ на все среды),
  `/api/` проксируется на бэк, `client_max_body_size 200m`, увеличенные таймауты, SPA fallback,
  gzip, кэш для хэшированных ассетов, `/healthz`.
- `docker-compose.yml` для локальной проверки связки (наш фронт + их api).
- CI (позже): GitHub Actions → GHCR → ssh на VPS → `docker compose pull && up -d`.

## Список просьб к бэку (по приоритету)

(дополнено по итогам анализа конкурентов — пункты 7–9)

1. PNG-превью слайдов и montage (`render_slides_png`) + `preview_artifact_id`.
2. HTML-экспорт через API (`render_html`).
3. Влить `devin/async-job-lifecycle`.
4. Перерендер PDF и превью после repair (до/после).
5. Превью слайдов шаблона после analyze.
6. CORS или общий origin — у нас nginx-прокси, так что не обязательно.
7. **Ручка «только план»** и генерация по присланному (отредактированному) DeckPlan —
   для «сначала план, потом вёрстка» (у них уже есть `generate(deck_plan=...)` внутри, ADR-009).
8. Превью исправления до применения (dry-run repair: какие действия, какие issues закроет).
9. Повторный аудит новой ревизии после repair (+ её PDF) — финал цепочки доказательств.
