# Трассировка требований на веб-интерфейс

Здесь описана клиентская часть DeckDNA. Парсинг, планирование, вёрстку, проверки и создание файлов
выполняет [бэкенд](https://github.com/Ranel435/LCT-prezi-2026). «Реализовано» означает наличие
клиентского сценария, а не подтверждение качества серверного результата на любом шаблоне.
Пути и API семи шагов перечислены в [ARCHITECTURE.md](../ARCHITECTURE.md).

## Ключевые требования

| Требование | Что делает фронтенд | Что зависит от бэкенда |
|---|---|---|
| Три варианта одного содержания | Шаг «Стиль»: три направления и пробные слайды, сравнение, сборка одного или всех трёх; переключение готовых вариантов в доводке | Различия вёрстки и соответствие единому шаблону; [обоснование оси](VARIANTS.md) |
| Аудит D/N и выбор исправлений | Шаг «Доводка»: типы проверок, статусы, рамки, выбор проблем, предпросмотр при поддержке, repair, отклонение, журнал и повторный аудит | Полнота проверок и результат исправлений; [описание интерфейса](AUDIT_UI.md) |
| PPTX, PDF и HTML | Скачивание и запрос форматов, паспорт, проверка ревизий на том же шаге | Нативные объекты PPTX, актуальный PDF, доступность и содержимое HTML; наличие ZIP с HTML-оболочкой и PNG не закрывает требование разметки слайдов |
| Живая сборка | Этапы, события SSE, черновики и готовые превью, инспектор слайда, резервный опрос | Какие события и картинки доступны до окончания полной сборки |

## Функциональные требования

| ID | Требование | Реализация и границы |
|---|---|---|
| FR-01 | Произвольный PPTX | «Материалы» (`pages/intake`): общая загрузка, `.pptx`/`.potx`, типы файлов, прогресс, ошибки; извлечение шаблона выполняет сервер |
| FR-02, FR-03 | Правила шаблона, мастера, макеты, обычные слайды | Паспорт и детали ДНК (`widgets/design-dna`, блоки `pages/intake`) показывают полученные цвета, шрифты, размеры, макеты, предупреждения и пробелы. Полнота данных зависит от анализатора |
| FR-04 | Сохранение результата разбора | ДНК читается с сервера и скачивается как JSON из материалов |
| FR-05 | Элементы внутри фоновой картинки | Отдельного клиентского распознавания нет; зависит от анализатора |
| FR-06 | Тема, назначение, аудитория, пожелания | Идея одной фразой и файлы на шаге 1, уточнения и ответы на шаге 3; сессия хранит бриф. Отдельной формы старого брифа нет |
| FR-07 | Структура до вёрстки | «План» (`pages/plan`, `widgets/deck-plan`, `features/edit-deck-plan`): главная мысль, слайды, тезисы, визуализация, источники; правленый `deck_plan` передаётся в сборку |
| FR-08 | 10–15 слайдов либо число пользователя | Целевой объём передаётся в `brief.target_slide_count`, уточняется в вопросах и меняется правкой плана. Фактические начальные значения берутся из проекта/сессии; интерфейс не гарантирует 10–15 слайдов во всех путях |
| FR-09 | Содержание по брифу и материалам | Шаги «Что понял» и «Вопросы» позволяют проверить смысловые блоки, подтвердить выводы, добавить тезисы и выбрать действия при нехватке материала. Текст составляет сервер |
| FR-10 | Макет под содержание | Объяснения и образец доступны на шагах стиля и доводки при наличии серверных данных; выбор макета выполняет сервер |
| FR-11 | Новые композиции из токенов | Стратегии выбираются на шаге стиля; фактические композиции формирует сервер |
| FR-12, FR-13 | Нативные графики, таблицы, схемы и иконки | План и выводы показывают визуализацию, доводка — объяснение графика и альтернативы, паспорт — показатели редактируемости. Нативность экспортированных объектов зависит от бэкенда |
| FR-14 | Палитра шаблона | Паспорт материалов показывает правила, аудит — отклонения. При брендбуке можно выбрать приоритет; соблюдение палитры в файлах обеспечивает сервер |
| FR-15 | Три варианта и обоснование оси | `faithful`, `balanced`, `visual`, три пробных стиля, команда сборки всех трёх; [VARIANTS.md](VARIANTS.md). Обычный выбор одного стиля не создаёт три полные колоды |
| FR-16 | D/N в конвейере | Доводка показывает `deterministic_status` и `contextual_status`, тип каждой находки; контекстная проверка доступна при активном подключении или серверном `model_auto` |
| FR-17 | Визуализация проблем | `widgets/slide-inspector`: рамки по `bbox` на PNG либо PDF, выделение, подсказки; предупреждение при несовпадении ревизий |
| FR-18 | Выбор исправлений | Флажки исправимых проблем, одиночный и пакетный repair, dry-run при заявленной поддержке, отклонение с причиной |
| FR-19 | Результаты исправлений | Журнал использует outcomes сервера и повторный аудит. Результат по проблеме сверяется по `fingerprint` или резервной сигнатуре |
| FR-20 | Нативный PPTX | Кнопка скачивания в доводке и паспорт редактируемости. Клиент получает файл сервера, сам PPTX не верстает |
| FR-21 | PDF | Скачивание или запрос экспорта, превью через pdf.js, контроль актуальности ревизии |
| FR-22 | HTML | Действие включается по capabilities, 501 обрабатывается как недоступный формат. Текущий описанный бэкендом экспорт ZIP с PNG не подтверждает выполнение требования HTML-разметки |
| FR-23 | Версионируемые промпты и конфиги | «О системе» показывает `/skill/manifest`; хранение и применение — ответственность бэкенда |
| FR-24 | Привязка к версиям | Паспорт, сведения о проверках, `/version`, манифест и команда воспроизведения; недостающие версии не подставляются |
| FR-25 | Переключение и откат версий | Не реализовано в интерфейсе; версии доступны для просмотра |
| FR-26 | Объяснимость | Источники блоков и выводов, главная мысль плана, обоснование графика, различия стилей, объяснение слайда, данные проблем и журнал; полнота объяснений зависит от API |
| FR-27 | Изображения | В настройках подключения есть поле сервиса изображений с ограничением размера; отдельного действия создания изображений в семи шагах нет |
| FR-28 | Свободный чат | Не реализован; текущий сценарий состоит из семи шагов и действий над материалами/слайдами |

## Нефункциональные требования

| ID | Требование | Реализация и границы |
|---|---|---|
| NFR-01 | До пяти минут на колоду | Клиент показывает ход работы, серверные времена и сведения паспорта при наличии. Бюджет 300 секунд объявлен в конфигурации; время выполнения обеспечивает сервер |
| NFR-02 | Любой шаблон | Рабочие данные ДНК берутся из API без подстановки правил выданных шаблонов. MSW-фикстуры используются только в mock-режиме |
| NFR-03 | Открытые веса, Apache 2.0 / MIT, лимиты размера | Панель подключения содержит каталог и проверку размера по идентификатору: 35B для текста/анализа слайдов, 20B для изображений. Лицензия произвольного id и фактический запуск проверяются на сервере |
| NFR-04 | Расход ресурсов | Паспорт отображает `usage`, если оно заполнено; измерения выполняет сервер |
| NFR-05 | Масштабируемость | Статика за nginx, адрес API при старте контейнера; общую серверную нагрузку определяет бэкенд |
| NFR-06 | Разделение слоёв | FSD, публичные API слайсов, Steiger; серверный конвейер отделён от представления |
| NFR-07 | Тесты | Vitest и Testing Library, контрактные MSW-тесты, mock e2e трёх движков и отдельные live e2e; команды в [README.md](../README.md) |
| NFR-08 | Десктопные браузеры | Цель — текущая/предыдущая версии Chrome, Firefox, Safari и Яндекс Браузера от 1280 px. `es2022`, pdf.js legacy, локальные шрифты; Playwright использует Chromium, Firefox, WebKit. Отдельные прогоны Safari/Яндекс Браузера не настроены |
| NFR-09 | Воспроизводимый запуск | `package-lock.json`, `.env.example`, Dockerfile и Compose, `VITE_API_MODE` и `BACKEND_URL` |
| NFR-10 | Устойчивость | Необязательные новые ручки 404/405/501 дают отсутствие данных, основные ошибки имеют повтор; SSE восстанавливается по sequence, статусы опрашиваются резервно, файлы проверяются по ревизии |
| NFR-11 | Совместимый контракт инференса | Сессия подключения создаётся через API, токен не сохраняется в браузере. Внешние вызовы делает бэкенд |
