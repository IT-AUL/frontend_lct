# Трассировка требований кейса на веб-интерфейс

Таблицы связывают требования кейса с экранами и модулями этого репозитория. Идентификаторы
требований: FR — функциональные, NFR — нефункциональные, DOC — документация, SUB — сдача.
Функции парсинга, генерации, вёрстки, аудита и экспорта реализует бэкенд DeckDNA
(https://github.com/Ranel435/LCT-prezi-2026). Здесь описано только то, что делает интерфейс.

Статусы:

- **готово** — интерфейс выполняет свою часть требования;
- **частично** — часть сделана, недостающее указано;
- **зависит от бэкенда** — интерфейс готов показать данные или вызвать функцию, но API её пока
  не отдаёт или требование целиком выполняется на бэкенде;
- **не реализовано** — в интерфейсе этого нет.

## Функциональные требования

| ID | Требование | Как закрывает интерфейс | Статус |
|---|---|---|---|
| FR-01 | Импорт произвольного PPTX | Экран «Шаблон» (`src/pages/template`, `src/features/upload-template`): drag&drop или выбор файла `.pptx`/`.potx` до 200 МБ, прогресс загрузки, автоматический запуск анализа, опрос статуса, понятная ошибка разбора с предупреждениями анализатора, замена шаблона | готово |
| FR-02 | Декомпозиция шаблона: токены, макеты, мастера, типографика, лого и колонтитулы | Виджет «ДНК шаблона» (`src/widgets/design-dna`): палитра темы и фактически используемые цвета, шрифты «заявлено / на слайдах», шкала кеглей, поля и линии выравнивания, якоря, дерево мастеров и макетов, схемы макетов по плейсхолдерам, роли слайдов, неподдерживаемые элементы | частично: блоки, которые бэкенд не заполнил (часть полей Design DNA пустая), скрыты. Интерфейс называет их в панели «Что поняли» («Анализатор не вернул: …»). Часть данных берётся из `latest_analysis.package_inventory` |
| FR-03 | Правила из мастера, макетов и обычных слайдов | Панель «Что поняли» показывает, сколько макетов реально используется на слайдах, какой макет доминирует и сколько не используется ни разу, а также конфликты «шрифт заявлен / фактически другой» и цвета вне темы | зависит от бэкенда: извлечение правил из слайдов выполняет анализатор |
| FR-04 | Сохранение результата парсинга | Design DNA хранится на бэкенде и доступна по `GET /templates/{id}/design-dna`. Интерфейс показывает sha256 файла и версию парсера | готово: на экране шаблона кнопка «ДНК в JSON» скачивает манифест |
| FR-05 | Элементы, вшитые в фоновую картинку | — | не реализовано (опционально, бэкенд таких данных не отдаёт) |
| FR-06 | Бриф: тема, назначение, аудитория, пожелания | Экран «Бриф и контент» (`src/pages/brief`): назначение (фича, продукт, проект, инициатива, другое) — обязательное поле; аудитория, тон, язык, обязательные разделы, запрещённые утверждения; контент файлом (`.md`, `.txt`, `.json`, `.docx`, `.pdf`, `.xlsx`) или текстом, превью разобранного контента | частично: отдельного поля «Тема» нет, тема задаётся контентом. Бэкенд разбирает один файл контента, и интерфейс об этом предупреждает |
| FR-07 | Структура до вёрстки | Экран «План» (`src/pages/plan`, `src/widgets/deck-plan`): назначение каждого слайда, заголовок, идея, визуализация, источники в контенте, разделы, статистика. Кнопка «Пересобрать с теми же данными» | частично: без `features.plan_only` план строится внутри генерации и виден после неё. Редактор плана до вёрстки готов и включается сам, когда бэкенд заявит флаг в `/capabilities` |
| FR-08 | 10–15 слайдов по умолчанию, своё число | Поле «Число слайдов» от 3 до 40, по умолчанию 12 (или значение проекта). Уходит в `brief.target_slide_count` | готово |
| FR-09 | Текст генерируется из брифа и контента | Переключатель «Использовать языковую модель» и выбор провайдера. План показывает источник каждого слайда в контенте | зависит от бэкенда |
| FR-10 | Выбор макета под контент | Схемы макетов в ДНК; сравнение вариантов «слайд N во всех трёх» | зависит от бэкенда: причина выбора макета по слайду в API не приходит |
| FR-11 | Новые композиции из токенов | Стратегия `visual` на экране вариантов описана как композиция из токенов шаблона | зависит от бэкенда |
| FR-12 | Нативные графики и таблицы | План показывает, на скольких слайдах есть визуализация. Паспорт показывает число слайдов-картинок и долю нативного текста | зависит от бэкенда |
| FR-13 | Диаграммы, иконки, SmartArt-подобные схемы | — | зависит от бэкенда |
| FR-14 | Цвета графиков и изображений из палитры | Нарушения видны в аудите (`template.color_palette`) | зависит от бэкенда |
| FR-15 | Три варианта, обоснование оси | Интерфейс запрашивает три стратегии в одном прогоне (`src/pages/brief/lib/brief.ts`). Экран «Три варианта» (`src/pages/variants`, `src/widgets/variant-board`, `src/widgets/variant-compare`): ось одной фразой, обоснование и профиль каждой стратегии, метрики, миниатюры, сравнение «слайд N во всех трёх». Обоснование — в [VARIANTS.md](VARIANTS.md) | готово |
| FR-16 | Аудит D + N в пайплайне | Экран «Аудит» (`src/widgets/audit-workspace`): бейджи D/N по полю `deterministic`, статусы детерминированной и контекстной частей, запуск проверок моделью по сессии провайдера. Подробно — [AUDIT_UI.md](AUDIT_UI.md) | готово |
| FR-17 | Визуализация проблем на превью | Рамки по `bbox` поверх страницы PDF (`src/widgets/slide-inspector`), цвет по серьёзности, лента слайдов со счётчиками | готово. После repair картинка остаётся от предыдущей ревизии: бэкенд не перерисовывает PDF, интерфейс об этом предупреждает |
| FR-18 | Пользователь выбирает, что исправить | Флажки у исправимых проблем, «Исправить» в карточке, «Исправить выбранное», отклонение с причиной, журнал, «до / после», повторный аудит | готово |
| FR-19 | Автоисправление и объяснение, что исправлено | Журнал: исправлено, не удалось, отклонено — с правилом, действием и ревизией. Паспорт показывает упрощения (fallbacks), о которых сообщил сервис | частично: исправления, которые бэкенд делает сам до показа, отдельно не выделены |
| FR-20 | Экспорт PPTX нативными объектами | Экран «Экспорт» (`src/pages/export`, `src/features/export-deck`): скачивание PPTX текущей ревизии, доказательство редактируемости в паспорте (повторное открытие файла, ошибки OOXML, доля нативного текста, слайды-картинки, PEI) | готово |
| FR-21 | Экспорт PDF | Скачивание и создание PDF, в том числе по запросу, если PDF у варианта нет | частично: после repair бэкенд не собирает PDF новой ревизии, интерфейс помечает файл как устаревший |
| FR-22 | Экспорт HTML | Карточка HTML на экране экспорта. Включится, когда `/capabilities` заявит формат | зависит от бэкенда: API отвечает 501, в интерфейсе метка «Не реализовано сервисом» |
| FR-23 | Промпты и конфиги отдельными файлами | Панель «О системе» показывает манифест скилла (`/skill/manifest`): скиллы, промпты, конфиги, модели | зависит от бэкенда |
| FR-24 | Привязка результата к версиям | Паспорт: версии скилла и пайплайна, версии промптов, модели, хэши конфигов, предупреждение, если прогон собран не той версией скилла, что сейчас на сервере. У каждой проблемы аудита — версия правила или модель и промпт. «О системе» — версии сервиса, парсера, планировщика, правил. Команда воспроизведения прогона через CLI | готово |
| FR-25 | Переключение и откат версий скиллов | — | не реализовано: версии только показываются |
| FR-26 | Объяснимость | Панель «Что поняли» в ДНК (конфликты, пробелы), источники в плане, обоснование стратегий, в карточке проблемы — измерено против нормы, доказательства и предложенное исправление; журнал исправлений | частично: объяснения выбора макета для слайда в API нет |
| FR-27 | Генерация изображений (t2i не больше 20B) | В панели провайдера есть необязательное поле модели изображений с проверкой лимита 20B | не реализовано: в интерфейсе нет функций с генерацией изображений (задача финала) |
| FR-28 | Чат с агентом | — | не реализовано (опционально) |

## Нефункциональные требования

| ID | Требование | Как закрывает интерфейс | Статус |
|---|---|---|---|
| NFR-01 | Не больше 5 минут на колоду | Экран генерации: таймер против бюджета 300 с, итог «в пределах бюджета» или «превышен». Паспорт: общее время прогона против бюджета | готово (показ). Само время зависит от бэкенда и модели |
| NFR-02 | Любой шаблон, без хардкода | В интерфейсе нет имён макетов, цветов, шрифтов или координат из датасета: всё берётся из ответа API. Если данных нет, блоки ДНК скрываются, а не подставляются | готово |
| NFR-03 | Открытые модели Apache 2.0 / MIT, не больше 35B | Панель провайдера (`src/widgets/provider-panel`): предлагаются только модели с лицензией Apache-2.0 или MIT и ссылкой на Hugging Face; размер модели разбирается из её id, и значения больше 35B (больше 20B для изображений) не принимаются | готово для интерфейса. Лицензию произвольного id интерфейс проверить не может |
| NFR-04 | Стоимость генерации, токены | Блок расхода (токены, вызовы модели) в паспорте появится, если бэкенд заполнит `usage` | зависит от бэкенда |
| NFR-05 | Масштабируемость | Статический SPA за nginx, один образ на все окружения, адрес бэкенда задаётся при запуске. Состояние интерфейса хранится в API и браузере, у контейнера его нет | готово |
| NFR-06 | Прозрачное разделение слоёв | Экраны соответствуют слоям бэкенда (схема в [ARCHITECTURE.md](../ARCHITECTURE.md)). Код разбит по Feature-Sliced Design, границы проверяет Steiger в CI | готово |
| NFR-07 | Тесты | 59 файлов Vitest, 350 тестов (логика и компоненты), контрактный тест mock-API, 5 e2e-сценариев Playwright в `e2e/` на трёх движках, `e2e:live` на живом бэкенде. CI запускает линтеры, проверку типов, Vitest, сборку и e2e | готово |
| NFR-08 | Десктоп: Chrome, Firefox, Safari, Яндекс Браузер (текущая и предыдущая версии) | Сборка `es2022`, pdf.js в legacy-сборке ради предыдущих версий браузеров, шрифты подключены локально, ширина от 1280 px. E2E в Chromium, Firefox и WebKit | частично: отдельных автоматических прогонов в Safari и Яндекс Браузере нет, их представляют WebKit и Chromium |
| NFR-09 | Воспроизводимый запуск конфиг-файлом | `Dockerfile`, `docker-compose.yml` (с профилем бэкенда), `.env.example`, `package-lock.json`, CI | готово для фронтенда |
| NFR-10 | Устойчивость | Ошибки API показываются по конверту ошибки (код, этап, `request_id`) с повтором. Пустые или частичные данные не ломают экраны. Рамки за краем слайда обрезаются. Потерянный после перезагрузки запуск генерации объясняется | готово |
| NFR-11 | OpenAI-совместимый контракт к моделям | Панель провайдера создаёт сессию с `base_url`, токеном и моделями по ролям и запускает проверку возможностей. Токен не хранится в браузере | готово для интерфейса. Вызовы моделей делает бэкенд |
