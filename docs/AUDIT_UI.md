# Аудит в интерфейсе

Аудит выполняет бэкенд DeckDNA внутри генерации: вариант не считается готовым, пока не проверен.
Интерфейс показывает результат, даёт выбрать, что исправить, запускает исправление и сравнивает
результат с повторной проверкой. Правила аудита в интерфейсе не вычисляются. Экран:
`/projects/:projectId/runs/:runId/audit/:variantId?` (`src/pages/audit`, `src/widgets/audit-workspace`,
`src/widgets/slide-inspector`).

## 1. Два типа проверок: D и N

У каждой проблемы из API есть флаг `deterministic`. По нему интерфейс ставит бейдж:

- **D · правило** — детерминированная проверка кодом: геометрия, шрифты, цвета, плотность,
  целостность пакета. Результат воспроизводим. В карточке есть «измерено / норма» и версия правила
  (`provenance.rule_version`).
- **N · модель** — контекстная проверка языковой или визуальной моделью: смысл заголовка,
  соответствие содержимого, опора на источники, опечатки. В карточке есть уверенность модели
  (`confidence`), модель и версия промпта (`provenance.model_id`, `provenance.prompt_version`).

N-проверки запускаются отдельно кнопкой «Смысл моделью». Интерфейс вызывает
`POST /variants/{id}/audits` с `provider_session_id` активной сессии провайдера. Без сессии кнопка
объясняет, что нужно подключить провайдера в шапке. Счётчики D и N в сводке показывают статус
каждой группы из `AuditRun`: `deterministic_status`, `contextual_status` (готово, идёт, не запускались, ошибка).

## 2. Категории

Для навигации код правила (`rule_code`) сопоставляется с человеческим названием и категорией.
Словарь лежит в `src/entities/audit/model/rules.ts`. Он влияет только на отображение: если код
неизвестен, интерфейс показывает сам код.

| Категория | Правила | Тип |
|---|---|---|
| Шаблон и бренд | `template.font_family`, `template.font_scale`, `template.color_palette`, `template.anchor_position`, `template.layout_origin` | D |
| Вёрстка | `layout.out_of_bounds`, `layout.unintended_overlap`, `layout.edge_margin`, `image.aspect_ratio` | D |
| Текст и читаемость | `text.overflow`, `text.slide_clip`, `text.font_floor`, `accessibility.contrast` | D |
| Плотность | `density.bullet_count`, `density.bullet_length`, `density.table_size`, `density.chart_series`, `density.occupancy` | D |
| Целостность и редактируемость | `integrity.empty_slide`, `integrity.duplicate_slide`, `integrity.placeholder_text`, `integrity.package`, `editability.raster_only`, `chart.metadata` | D |
| Смысл (модель) | `content.conclusion_title`, `content.title_alignment`, `content.single_message`, `content.source_support`, `content.nonempty`, `content.visual_relevance`, `content.prompt_leakage`, `content.spelling`, `content.data_relevance`, `deck.logical_flow` | N |

Всего 24 детерминированных правила и 10 контекстных проверок. Полный список с отметкой
«исправляется автоматически» есть в панели «О системе».

## 3. Устройство экрана

- **Сводка** (`AuditSummary`): выбор варианта, число открытых проблем по серьёзности (блокер,
  ошибка, предупреждение, инфо), счётчики D и N со статусом, кнопки «Смысл моделью» и «Повторный
  аудит», переход к экспорту.
- **Полоса категорий** (`PolicyStrip`): число открытых проблем в каждой категории. По клику список
  фильтруется по категории.
- **Лента слайдов** (`SlideFilmstrip`): миниатюры из PDF, у каждой счётчик открытых проблем и цвет
  самой серьёзной из них.
- **Слайд с рамками** (`SlideInspector`, `IssueOverlay`): страница PDF и поверх неё рамки проблем по
  `bbox` в нормированных координатах [0, 1]. Цвет рамки соответствует серьёзности, отдельный цвет
  у исправленных проблем. При наведении или выборе рядом с рамкой появляется подпись «D/N ·
  название». Рамки, которые выходят за слайд, обрезаются по краю и помечаются «за краем слайда».
  Выбор рамки открывает карточку в списке, и наоборот.
- **Список проблем** (`IssueList`, `IssueCard`): по умолчанию группировка **по правилу** — группы
  свёрнуты, у каждой счётчик «×N» и общий флажок; одинаковые находки на одном слайде слиты в одну
  строку «×3». Сверху итог «108 находок · 6 правил · 54 исправимо». Можно переключить на группировку
  по слайдам или категориям. Фильтры по типу (D/N), серьёзности, статусу (открытые, решённые, все)
  и флаг «только исправимые». В карточке: человеческое сообщение, измеренное значение против нормы
  с единицами, предложенное исправление, действия «Исправить» и «Отклонить…»; сырые данные бэкенда
  (`evidence`, id фигур, версия правила) — в раскрывающемся блоке «Технические детали». У проблем без
  автоисправления — неактивный флажок «Только вручную».
- **Клавиатура**: `j` / `k` или стрелки вверх и вниз — по проблемам, стрелки влево и вправо — по
  слайдам, `x` — выбрать проблему, `Esc` — снять выделение. Если фокус на кнопке, ссылке, радиокнопке,
  вкладке или флажке, стрелки остаются у них.

## 4. Выбор и исправление

1. **Что можно выбрать.** Флажок есть только у проблем, которые можно исправить автоматически.
   Для этого должны выполняться два условия: бэкенд поставил `repairable: true`, и у правила есть
   обработчик исправления. Второе условие нужно, потому что сейчас бэкенд ставит `repairable: true`
   и правилам без обработчика, и такие проблемы после repair остаются нерешёнными. Список правил с
   обработчиком ведётся по планировщику исправлений бэкенда: это поле `autoFix` в словаре, сейчас 13 правил.
2. **Запуск.** «Исправить» в карточке исправляет одну проблему, панель внизу списка — все выбранные
   («Исправить выбранное (N)», «Выбрать исправимые»). Интерфейс отправляет
   `POST /audits/{id}/repairs` с `selected_issue_ids`, `max_iterations: 2` и сессией провайдера, если она
   есть, затем читает job со счётчиками сервиса.
3. **Новая ревизия.** Бэкенд применяет действия к PPTX, создаёт ревизию `r{N+1}` и проверяет её заново.
   Интерфейс сбрасывает кэш аудита, варианта и проблем и загружает новый список.
4. **Отклонение.** «Отклонить…» требует причину: готовую («Так задумано», «Ложное срабатывание»,
   «Поправлю в PowerPoint») или свою. Уходит `POST /issues/{id}/dismiss`. Отклонённые проблемы
   остаются в журнале вместе с причиной.

## 5. Журнал

После repair у проблем в новом аудите **другие id**. По отдельной проблеме бэкенд отдаёт только
общие счётчики, поэтому итог по каждой выбранной проблеме интерфейс определяет сам
(`src/entities/audit/lib/journal.ts`):

- сигнатура проблемы — `rule_code | номер слайда | отсортированные shape_ids`;
- если сигнатуры выбранной проблемы нет среди открытых и нерешённых проблем новой ревизии, она
  отмечается «исправлено», иначе «не удалось» (одинаковые сигнатуры считаются поштучно);
- во вкладке «Журнал» видны записи «исправлено», «не удалось» и «отклонено» с ревизией, названием
  правила и действием, а также итог каждого запуска: сколько запрошено, исправлено и не удалось,
  плюс счётчики сервиса (применено, пропущено, не удалось);
- журнал хранится в `localStorage` браузера отдельно для каждого варианта и фильтруется по текущей
  ревизии аудита.

## 6. До / после

Режим «До / после» в инспекторе слайда:

- **До** — страница PDF и рамки проблем, которые менялись на этом слайде.
- **После** — список действий над PPTX с итогом каждого (исправлено, не удалось, отклонено), кодом
  правила и ревизией.

Картинки «после» нет: бэкенд после repair не перерисовывает PDF. Интерфейс пишет об этом прямо.
Если PDF старше ревизии аудита, рамки рисуются пунктиром и над слайдом стоит пометка «Превью
устарело: картинка rX, проблемы rY». Рамки невыбранных проблем приглушены; переключатель «Все
рамки» показывает или скрывает их.

## 7. Повторный аудит

- После каждого repair бэкенд проверяет новую ревизию. Интерфейс показывает баннер «Повторный
  аудит: 0 блокеров» с дельтой («ошибок 54 → 53 · исправлено 1») и ссылкой на экспорт или «Повторный
  аудит: N блокеров» с подсказкой исправить или отклонить их с причиной. Критерий — блокеры: часть
  ошибок бэкенд пока не чинит автоматически, и «0 ошибок» был бы недостижим.
- Шапка проекта на аудите и экспорте показывает «Ждёт решения: N критич.», «Критичных проблем нет»
  или «Готово к экспорту».
- Кнопка «Повторный аудит» заново запрашивает аудит текущей ревизии и список проблем.
- Когда после исправлений (ревизия старше r1) не осталось блокеров, в «цепочке доказательств»
  проекта появляется отметка «Повторный аудит: 0 блокеров».

## 8. Ограничения бэкенда и как интерфейс с ними работает

| Ограничение | Как в интерфейсе |
|---|---|
| Нет PNG-превью слайдов | рамки рисуются поверх страницы PDF (pdf.js). Если PDF нет, рамки на пустом листе с пропорциями слайда |
| После repair PDF и паспорт не пересобираются | картинка от предыдущей ревизии с предупреждением; «после» показано списком действий; в экспорте файлы помечены как устаревшие |
| Нет результата repair по каждой проблеме и стабильных id | журнал по сигнатуре (раздел 5) |
| `repairable: true` у правил без обработчика | выбрать можно только правила с обработчиком (раздел 4) |
| N-проверки требуют сессию провайдера и модель | отдельная кнопка «Смысл моделью», статус N в сводке; без сессии — подсказка |
| Нет предпросмотра исправления до применения (dry-run) | в карточке показано планируемое действие по правилу, но фактический результат виден только после repair |
| Список проблем без курсорной пагинации | загружается до 200 проблем на аудит. В записанных прогонах бывает 74–108 проблем на вариант |
| Некоторые `bbox` выходят за слайд | для правил выхода за границы это корректно: рамка обрезается и помечается |
